Offline-first forms without a frameworkWhat nine months of offline-first forms taught me about saving, syncing, and telling people the truth about both

Fieldnote's surveyors work in basements with no signal. This is the small sync layer that made every answer safe the moment it was tapped, in plain TypeScript and IndexedDB.

EngineeringFormsOffline

Save on tap, sync later

The first version saved a form when the surveyor pressed Save. In a basement, Save meant a spinner, then an error, then a lost hour. The fix was to stop treating the server as the place where answers live.

Now an answer is written to IndexedDB the moment it is tapped. A queue sends it later, when the tablet finds a network. The surveyor never waits, and never wonders.

One queue, four states

The whole layer is a queue and a status. Each answer is in exactly one state, and the header shows the state of the oldest answer still waiting.

export async function answer(id: string, value: unknown) {
  await db.put("answers", { id, value, at: Date.now() });
  queue.push(id);       // sent when the network comes back
  setStatus("saved");   // shown at once, never waits for a server
}

That is most of it. The queue retries with a backoff, and setStatus only ever moves forward unless a conflict comes back.

I stopped checking whether it saved. It always says.

Ana, building surveyor

Tell the truth about sync

Three rules came out of the site visits, and the code enforces all three.

  • Show the state of the data, not of the network. "Offline" says nothing about whether my answer is safe.
  • A conflict names both values and who wrote them. "Sync failed" is not a decision anyone can make.
  • Nothing is lost silently. An answer still unsent after a day is reported to the surveyor, by name.

What I would change

I wrote the queue by hand to keep it small: 140 lines with tests. With hindsight I would call navigator.storage.persist() from day one. Two tablets came close to losing data to storage pressure before we added it.
